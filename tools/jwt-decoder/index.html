JWT 解码

把 Token 粘进来，立刻拆成头部、载荷、签名三段：头部与载荷按 JSON 着色展开， exp / nbf / iat 换算成本机时区的时间与剩余时长，alg=none、 crit、jku 这类要留神的头字段单独标出来。 签名只展示字节，不在这里校验。

已上线 本地运行 不校验签名

只解码，不校验签名。解码成功不代表这个 Token 有效 —— 任何人都能照着原样拼一个载荷一模一样、签名随便填的 Token。 要判断真伪，必须拿签发方的密钥自己验签（下面「怎么自己校验签名」给了命令）。

三段是怎么来的

  • JWT 用的是 JWS 紧凑序列化：base64url(头部).base64url(载荷).base64url(签名)， 三段之间用点号连接。
  • 所谓 base64url 就是把标准 base64 的 + / 换成 - _，并把末尾的 = 全部省略。 段里出现 + 或 = 都会被本站标出来。
  • 未签名的令牌（头部写 "alg":"none"）第三段是空字符串， 所以看起来只有两段半。只写两段的写法本身不合规范，会被提示。
  • 5 段是 JWE（加密令牌，RFC 7516），结构是 头部.加密密钥.初始向量.密文.认证标签。载荷是密文，本站只能解出第一段的头部。

七个注册声明的含义

  • iss 签发者 · sub 主体（通常是被描述的用户）
  • aud 受众（接收方，可以是字符串或数组）
  • exp 过期时间 · nbf 生效时间 · iat 签发时间 —— 三者都是秒数
  • jti 令牌编号，用于防重放
  • 其余键名不属于规范，本站照原样列出并标成「自定义声明」，含义要看签发方的文档。

「时效」这一栏是怎么判的

  • 只拿 exp 与 nbf 跟你本机的时钟比： 现在 ≥ exp 算过期，现在 < nbf 算尚未生效。
  • 它不代表签发方也这么认为 —— 两边时钟有偏差时结论就会不同； 也不代表服务器会接受这个令牌（受众、签发者、作用域都要单独核对）。
  • 两个都没有时显示「无时效声明」，这类令牌要么长期有效，要么有效期由签发方另外记着。
  • exp 超过 100000000000（看起来是毫秒时间戳，即 13 位）时会被单独标出来 —— 规范要求的是秒，按秒解释会得到公元五万年以后的日期。

怎么自己校验签名

  • 先取出签名输入：头部.载荷 这半截（含中间的点）， 用文本原样存成 input.txt（末尾不要加换行）。
  • 把第三段转回二进制：printf '%s' "第三段" | tr '_-' '/+' | base64 -d > sig.bin （base64url 转标准 base64 就是 - → +、_ → /）。
  • HMAC 类（HS256/384/512）： openssl dgst -sha256 -mac HMAC -macopt hexkey:<密钥的十六进制> -binary input.txt | openssl base64 | tr -d '=' | tr '+/' '-_'， 结果应与第三段逐字符相同。
  • RSA / ECDSA 类（RS/ES/PS 开头）： openssl dgst -sha256 -verify pub.pem -signature sig.bin input.txt， 输出 Verified OK 才算过。 注意 ES256 / ES384 这类：JWS 里的签名是原始的 R‖S 拼接，而 openssl 要的是 DER 结构， 直接喂进去会报验签失败 —— 得先把 sig.bin 转成 DER（openssl asn1parse -genconf 拼出 SEQUENCE，或改用专门处理 JWS 的库）。
  • alg 为 none 时没有签名可验，任何人都能伪造，不要在线上用它。

关于安全的两句话

  • 本站不联网，Token 只在这台设备上解码，也不会被写进任何存储 —— 但生产环境的 Token 本身就是凭据，贴进任何在线工具之前都要想一下这件事。
  • 复制出去的永远是解出来的原文，不是屏幕上那份带序号、有着色的视图。
