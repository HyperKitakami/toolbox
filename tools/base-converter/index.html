为什么用 BigInt 而不是 Number

  • JavaScript 的 Number 是 64 位双精度浮点， 能精确表示的最大整数是 2⁵³ − 1（约 9007 万亿）。 再大就只能存近似值：Number('0xffffffffffffffff') 得到 18446744073709552000 —— 最后几位已经错了。
  • 进制转换的典型用途（位运算、颜色、内存地址、哈希、编码）本来就经常落在 64 位范围里，所以本工具从解析到输出全程用 BigInt，几百位的整数也一位不差。
  • 不用 0n 这种字面量，而是 BigInt(0) 调用形式 —— 字面量是解析期语法，老引擎加载整个脚本就会失败； 调用形式只是运行时不可用，可以检测后给出明确提示。

负数与补码

  • 默认情况下负数按符号 + 绝对值显示：-255 → -ff。这不是补码。
  • 补码只在特定位宽下才有意义 —— -1 在 8 位下是 0xff，在 16 位下是 0xffff。 所以选了「8 位」之后，-1 的二进制与十六进制才会按补码显示 （1111 1111 / ff）。
  • 位宽同时会让非负数左侧补零：选 8 位时 5 显示成 0000 0101 / 05， 方便直接对着位模式读。
  • 补码只作用于二进制与十六进制。八进制和十进制的补码写法没人用， 加了只会让人怀疑哪个才是对的。
  • 值超出该位宽的有符号范围时（比如 300 放进 8 位）不会截断，而是给出提醒并按 任意精度原样显示 —— 静默截断会让人拿到一个错的位模式。

前缀与分隔符

  • 0x / 0X 表示十六进制、 0b / 0B 表示二进制、 0o / 0O 表示八进制。 前缀优先于源进制选择，与编程语言里的整数字面量规则一致。
  • 前缀解释失败时不会悄悄改用你选的源进制 —— 0b1f 就是语法错误，不会因为源进制选了 16 就变成 0x0b1f。要按十六进制解析就写成 0x0b1f 或去掉前缀。
  • 输入里的空格、下划线、逗号会被剥掉，所以 1010 1010、1010_1010、 1,234,567 都能直接粘进来。
  • 数字大小写不敏感：FF 与 ff 一样。 输出的大小写由「十六进制用大写」开关决定。

为什么不支持小数

  • 十进制小数在二进制下大多是无限循环的： 0.1 的二进制是 0.0001100110011…， 永远写不完。
  • 要显示就只能截断，而截断多少位取决于你要干什么用 —— 给一个「保留 16 位」的默认值，很容易被当成精确值拿去用。
  • 而进制转换的实际用途（位运算、颜色、内存地址、编码）全是整数。 所以带小数点的输入会直接报错，而不是给一个看起来像答案的近似值。
  • 确实需要二进制小数的话：整数部分用本工具转，小数部分用「乘 2 取整」手算； 或者查一下这个浮点数的 IEEE 754 位模式。
