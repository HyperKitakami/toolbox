四种单位怎么认

  • 秒（10 位） —— 经典 Unix 时间戳，如 1717200000。 date +%s、PHP time()、 大多数后端 API 用的是这一档。
  • 毫秒（13 位） —— JavaScript 的 Date.now()、 Java 的 System.currentTimeMillis()，如 1717200000000。
  • 微秒（16 位） —— Python 的 time.time() 取整到微秒、 MySQL 的 TIMESTAMP(6)。
  • 纳秒（19 位） —— Go 的 UnixNano()、 Rust 的 SystemTime、ClickHouse 的 DateTime64(9)，如 1717200000000000000。
  • 「自动」按数量级分档（<10¹¹ 秒、<10¹⁴ 毫秒、 <10¹⁷ 微秒、再往上纳秒），判定结果写在输入框下面。 边界上本来就有歧义，判错了在「纯数字输入的单位」里点一下改过来即可。

裸日期为什么容易踩坑

  • 按 ECMAScript 规定，2026-06-01 这种只有日期的写法 按 UTC 零点解释；而 2026-06-01T00:00:00 这种带时间但没带时区的写法按本地零点解释。
  • 于是两个看起来差不多的写法在 UTC+8 下相差 8 小时 —— 2026-06-01 得到 2026-06-01T00:00:00Z， 2026-06-01T00:00:00 得到 2026-05-31T16:00:00Z。 这不是工具算错了，是规范就这么定的。
  • 遇到裸日期时，状态行会把实际采用的口径和对应的本地时间一起写出来。 想让裸日期也按本地零点算，打开上面的开关。
  • 跨时区协作时，日期一律带上时区后缀（Z 或 +08:00）最省事 —— 不带后缀的写法含义取决于读它的人在哪。

时区与夏令时

  • 时间戳本身是与时区无关的：同一个瞬间，全世界的时间戳都一样。 时区只影响「显示成什么墙上时间」。
  • 时区对照表里的偏移是该时刻的偏移，已经考虑夏令时。 同一个时区在夏天和冬天的偏移可能差一小时 （比如 America/New_York 是 −05:00 或 −04:00）。
  • 时区名用的是 IANA 数据库的写法（Asia/Shanghai、 Europe/Berlin），不是 CST 这种缩写 —— 缩写 CST 同时代表中国标准时间、美国中部时间与古巴标准时间， 三个地方差 13 个小时。
  • 中国全境统一使用 UTC+8，没有夏令时；Asia/Urumqi 在 IANA 数据库里是 UTC+6 的历史遗留条目。

口径与范围

  • 相对现在按「一年 = 365 天、一月 = 30 天」估算， 所以「1 年前」是 365 天前而不是日历上的同一天。这个口径与上游一致。
  • 秒的取值用 Math.floor(毫秒 / 1000)， 与 date +%s 一致（1970 年之前的时间戳会向负方向取整）。
  • 可表示的日期范围由 JavaScript 的 Date 决定，约公元 ±27 万年。 年份超出 1–9999 时会给出提醒 —— 多数系统的时间库处理不了这个范围。
  • 只处理公历。1582 年之前的日期按前推公历（proleptic Gregorian）计算， 与当时实际使用的儒略历不一致。
