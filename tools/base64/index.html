Base64 编解码

把文本按 UTF-8 编码成 Base64，或把 Base64 解回文本。默认自动判定方向， 也可以手动指定；支持 URL 安全字符集（- _，省略填充）， 文件可以直接拖进来转成 Base64 与 Data URL。 解出来的字节不是 UTF-8 文本时（比如图片、压缩包）， 这里会给一份十六进制字节视图，而不是含糊地说一句「无效」。

这四种写法其实是同一回事

        
    
          
  • 标准 Base64（RFC 4648 §4）：用 + 和
            /，末尾按需补 =。
    • 
          
  • URL 安全（RFC 4648 §5）：把 + / 换成
            - _，并按规范省略末尾的 =。
            目的是让它能安全地放进 URL、文件名和 JWT 里（+ 在 URL 里
            表示空格、/ 是路径分隔符、= 会被转义）。
    • 
          
  • 所以「URL 安全」这个开关只影响结果怎么写。
            解码时两种字符集都收 —— 不管有没有勾，带 - _
            或缺少 = 的串都能解开。
    • 
          
  • 同理，填充（=）只是书写习惯：缺少时本站会补上再解，
            多了或者位置不对才会报错 —— 那说明串被截断或拼接了。
    • 
        

      

      

        
「自动判定方向」是怎么判的

        
    
          
  • 依次过四道闸门：字符集与长度合法 → 真的能解开 → 解出来的字节是
            合法的 UTF-8 文本 → 并且不是纯字母串。
            四条全过才当成 Base64 去解码，否则按普通文本编码。
    • 
          
  • 为什么要这么严：只看字符集与长度的判法会把大量普通英文单词认成 Base64。
            拿 EFF 的 7776 个常用英文单词逐个实测，只看字符集时
            6103 个（78.5%）会误判；加上后面两道闸门后是 0 个。
    • 
          
  • 代价是漏判，而且是两个方向都漏：全字母又没有填充的
            Base64（如 YWJj），以及解出来是二进制的 Base64
            （比如图片的），都会被当成文本。这种情形点一下「Base64 解码」就行 ——
            宁可漏判也不误判，漏判只是多点一下，误判会把正常文本搅成一串乱码或
            一份毫无意义的字节视图。
    • 
          
  • 第二种漏判不会让你两头落空：编码结果的状态行会告诉你
            「这串本身也是合法的 Base64，解出来是 N 字节的非文本内容」，
            并指路到「Base64 解码」。
    • 
          
  • 拿不准就把「自动判定方向」关掉，两个按钮完全按你点的走。
    • 
        

      

      

        
为什么「解码」有时候会说解出来不是文本

        
    
          
  • Base64 能编码任意字节，并不保证那串字节是文本。UTF-8 的字节有固定结构
            （首字节的前几位决定后面跟几个延续字节），不合法的字节序列就还原不成字符串。
    • 
          
  • 这种情况下结果区给的是一份十六进制字节视图，状态行说明解出了多少字节。
            少了这份视图，工具在你手里就废了 —— 上游在这一步报的是一句
            Invalid Base64 string，而那个串其实完全合法，
            报出来的原因不是真原因。
    • 
          
  • 要处理图片、压缩包这类内容，用下面的「文件转 Base64」：那条路读的是原始字节，
            不做文本解码，任何文件都能转。
    • 
        

      

      

        
体积、填充与换行

        
    
          
  • 每 3 个字节编成 4 个字符，所以体积固定膨胀约 1/3（×1.33）。
            剩下 1 个字节补 ==，
            剩下 2 个字节补一个 =。
    • 
          
  • 统计面板里的「结果 / 输入」在编码方向就是实际膨胀倍数、在解码方向是还原比。
    • 
          
  • 折行不影响解码。邮件与 MIME 里的 Base64 每 76 个字符折一次行，
            粘贴进来照样能解 —— 本站会先剥掉所有空白（空格、制表符、换行）再判定与解码。
            折行会改变「输入字符数」，所以那个数字比纯 Base64 长度大，是正常的。
    • 
          
  • 编码结果不会替你折行，永远是一整行。
