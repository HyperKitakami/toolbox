URL 编解码

把网址、查询参数和路径段做百分号编码或解码。三种模式对应三套口径， 空格与 + 可以互转。解码失败时这里会指出 是第几个字符、哪几个字节不合法，而不是含糊地报一句「无效」； 网址还会被拆成协议、主机、路径、查询参数与片段逐条列出。

百分号编码在做什么

        
    
          
  • URL 里只允许出现一小撮 ASCII 字符，其余一律要写成 %
            加两位十六进制 —— 这就是「百分号编码」（也叫 URL 编码）。
    • 
          
  • 被编码的单位是字节，不是字符。文本先按 UTF-8 变成字节，
            再逐个字节编码。所以一个汉字是 3 个字节 → 9 个字符
            （中 → %E4%B8%AD），
            一个 emoji 是 4 个字节 → 12 个字符。这也是中文网址看起来很长的原因。
    • 
          
  • RFC 3986 §2.3 把 A–Z a–z 0–9 - . _ ~ 定为
            非保留字，它们永远不需要编码；其余字符该不该编码，
            取决于它出现在 URL 的哪个位置 —— 这就是三种模式的由来。
    • 
          
  • 十六进制大小写都合法（RFC 3986 建议大写，本站默认大写），
            解码时两种都收。
    • 
        

      

      

        
三种模式的区别

        
    
          
  • 组件（encodeURIComponent）：
            除了非保留字与 ! ' ( ) * 全部编码。
            处理查询参数值、路径段用这个 ——
            a/b?c=d → a%2Fb%3Fc%3Dd。
    • 
          
  • 整条 URL（encodeURI）：
            额外放行 ; , / ? : @ & = + $ # 这些分隔符，
            所以整条网址编完之后结构还在：
            https://a.com/b?c=d 里只有空格这类真需要编的东西会变。
    • 
          
  • 严格（RFC 3986 字面口径）：只放行非保留字，连
            ! ' ( ) * 都编码。
            JWT、OAuth 1.0 的签名基串要的是这一种 —— 那里把 !
            留着不编码会导致签名对不上，而大多数语言的 urlencode
            默认不编它们。
    • 
          
  • 模式同时管两个方向。「整条 URL」模式下解码会保留
            分隔符的转义：%2F 保持原样，因为它是路径段里的
            字面斜线，解成 / 就成了分隔符、把 URL 的结构改掉了
            （与 decodeURI 一致）。要把它解出来就用「组件」模式。
    • 
        

      

      

        
空格、+ 与 %20

        
    
          
  • 路径里的空格标准写法是 %20；而在
            application/x-www-form-urlencoded
            里（表单提交、绝大多数查询串），空格写成 +。
            同一个 URL 里两套写法并存是常态。
    • 
          
  • 所以「空格编码为 +」与「解码时 +
            视为空格」是一对配套开关，默认都关 ——
            默认关掉才是可逆的：不知道上下文就假定 + 是空格，
            会把 C++ 解成 C  。
    • 
          
  • 判「+ 是不是空格」看的是输入里那个字符。
            %2B 解出来永远是字面的加号，不会被再当成空格。
    • 
          
  • 首尾空格不会被吃掉。这里不做 trim：
            粘贴时多带一个空格是常见事故，工具悄悄替你删掉才是真麻烦。
    • 
        

      

      

        
解码为什么会失败

        
    
          
  • 转义不完整：出现一个 %，后面不是两位十六进制
            （%.5、%2G、结尾孤零零的
            %）。想表示字面的百分号，写法是 %25。
    • 
          
  • 字节序列不是合法 UTF-8：多字节字符被截断、续接字节位置不对、
            过长的编码、代理项码位…… 百分号编码只保证字节被原样搬运，
            不保证那串字节是文本。
    • 
          
  • 这两种情况这里都会给出第几个字符、哪几个字节。
            原生 decodeURIComponent 抛的是一句
            URI malformed，没有位置也没有原因，对着几百个
            % 只能一个个数。
    • 
          
  • 如果字节按 GBK 能解开，状态行里会附一句推测值 ——
            老站点用 GBK 编码查询串很常见（%C4%E3 就是「你」），
            但浏览器只认 UTF-8，原生接口只会报错。这里说清是推测，不冒充结论。
    •
