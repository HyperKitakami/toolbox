哈希摘要生成

同一份内容，五种摘要一次算完：MD5、SHA-1、SHA-256、SHA-384、SHA-512。 输入的文本按 UTF-8 编码成字节再算 —— 和 sha256sum、Git、OpenSSL 的默认口径一致； 也可以直接拖一个文件进来算校验和。

已上线 本地运行 输入不上传 · 不保存

哈希不是加密。摘要是单向的 —— 从摘要推不回原文， 所以这个页面只是把内容压成一串指纹，不保存内容本身：不发网络请求、不写 localStorage、不进 URL。这个页面 没有草稿功能，是有意不做的，刷新即清空。 另外提醒一句：文本框里的内容是明文显示的（不然没法核对你要算的是什么）， 所以如果你打算算的是一段口令，先确认这台机器是你自己的。

哈希是什么，不是什么

  • 把任意长度的字节压成固定长度的一串（摘要）。同样的输入永远得到同样的摘要， 输入改一个比特，输出就面目全非。
  • 它是单向的：从摘要推不回原文，这是刻意设计的。所以它 不是加密 —— 加密可以解密，哈希不可以。别拿它当「加密」用。
  • 它回答的是「这两份内容是不是同一份」。当内容从你眼前经过时， 它能查出传输过程中有没有损坏；但能不能查出 被人故意换掉，取决于这个算法有没有被攻破 —— 见下一条。

MD5 与 SHA-1 已经不能用于签名

  • RFC 6151 的原文：MD5 is no longer acceptable where collision resistance is required such as digital signatures. It is not urgent to stop using MD5 in other ways… —— 意思是：需要「抗碰撞」的地方（数字签名、证书、 防篡改）不能用 MD5；只是拿来比对内容有没有变（校验和），不着急停用。
  • SHA-1 同理。RFC 6194 记着 NIST 从 2010 年起就建议不要再用 SHA-1 生成数字签名， 而碰撞的成本一路在降：2005 年找到完整 80 轮的碰撞需要 269 次运算， 2017 年 Google 与 CWI 造出了两份内容不同、SHA-1 却完全相同的 PDF （就是 SHAttered）。
  • 所以这个页面给 MD5 与 SHA-1 都标了「已破 · 别用于签名」。 拿来跟官网公布的校验和比对（防下载损坏）仍然可以； 拿它证明「这份文件没被人换掉」则是错的 —— 攻击者可以造出两份摘要相同的文件， 让你核对通过、却装上了另一份内容。
  • 要抗碰撞，用 SHA-256 或更强。这也是为什么现在的软件下载页基本都只给 SHA-256。

摘要算的是字节，不是字符

  • 同一段文本换个编码就是另一串字节、另一个摘要。这个页面统一用 UTF-8 —— 和 sha256sum、 Git、OpenSSL 的默认口径一致，所以结果拿去跟命令行对照能对上。
  • 换个编码就换一个结果：把「中文」用 GBK 存成文件再拖进来，摘要当然不一样。 这不是工具算错了，是输入本来就不是同一串字节。
  • 顺带说一件上游实现真错了的地方：原来的版本里，MD5 吃的是 JS 字符串的 UTF-16 码元、而 SHA 系列走 UTF-8，两套字节 —— 于是同一个字符串粘进文本框和存成文件拖进来，MD5 不一样。 现在所有算法都只吃字节，文本统一走 UTF-8。

十六进制还是 Base64

  • 十六进制（小写）是 sha256sum / certutil -hashfile 的输出格式， 也是技术文档里最常见的写法。
  • Base64 更短，而且是子资源完整性 （Subresource Integrity）要求的写法：<script integrity="sha384-…"> 里那一串就是 SHA-384 的 Base64。 给 CDN 资源写 integrity 时选这个。
  • 比对框两种格式都认，也可以互相比：当前显示 Base64、你粘十六进制进来，照样能对上。

文件为什么有 128 MB 的上限

  • 浏览器的 crypto.subtle.digest 是一次性接口： 没有「喂一段、再喂一段」的流式更新（WebCrypto 至今没提供）， 所以必须先把整个文件读进内存。读 500 MB 就占 500 MB， 还可能让页面卡住甚至崩掉。
  • 纯 JS 那条回落路径同样是整块算的，所以这个限制与走哪条实现无关。
  • 更大的文件请用系统自带的工具：Linux / macOS 用 sha256sum 文件名，Windows 用 certutil -hashfile 文件名 SHA256。 这两个都是流式的，几个 GB 也不占内存。
  • 文件内容的摘要按原始字节算，不经过 UTF-8 那一步 —— 编码只作用于文本框里的内容。

和「TOTP 动态口令」「Base64 编解码」的分工

  • 三个工具共用同一份密码学实现（js/hash-utils.js， 即 T.hash）：摘要、HMAC、Base32 都在那里。 所以这里的 SHA-1 与 TOTP 用的 SHA-1 是同一次实现，不会出现「两边算出来不一样」。
  • 要算 HMAC（带密钥的摘要）等 hmac-generator， 要编码字节去 Base64 编解码。
  • MD5 没有浏览器原生实现（WebCrypto 有意不实现它），所以这一行永远走纯 JS； SHA 系列在安全上下文里走浏览器原生实现。底栏会写明当前用的是哪条路。

来源与致谢

  • 算法按 RFC 1321（MD5）、FIPS 180-4 / RFC 6234（SHA 系列）实现， 官方向量与 OpenSSL 逐条比对过。
