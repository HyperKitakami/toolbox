UUID 生成器

批量生成 UUID。默认用 v4（122 位全随机）；要做数据库主键就用 v7 —— 前 48 位是毫秒时间戳，同一毫秒内也按生成顺序递增，排序即插入顺序。 老系统要 v1 也有，附带一个格式校验器。

三个版本怎么选

  • v4（随机） —— 122 位全是随机数。最通用，什么都不用想，绝大多数场景直接用这个。
  • v7（时间有序） —— 前 48 位是毫秒时间戳，后面 74 位里 12 位做单调计数器、 62 位是随机数。排序即插入顺序，做主键时对 B+ 树索引最友好。 新项目该用它，而不是 v1。
  • v1（时间戳） —— 60 位时间戳 + 时钟序列 + 节点标识。只有要对接老系统时才用： 它会把「同一台机器」写进 UUID，可被追踪，而且时间戳精度只有 100 纳秒、排序上不如 v7 直接。
  • RFC 9562 的原话是「Implementations SHOULD utilize UUIDv7 instead of UUIDv1 and UUIDv6 if possible」—— 能选 v7 就别选 v1。

v7 为什么要在同一毫秒里也递增

  • 只用毫秒时间戳的话，同一毫秒内生成的一批 UUID 之间没有顺序 —— 而「能按时间排序」正是 v7 相对于 v4 的全部价值。
  • RFC 9562 §6.2 专门点了这个场景：「if one thousand UUIDs are generated for the same timestamp, there should be sufficient logic for organizing the creation order of those one thousand UUIDs」，并给出了三种做法。
  • 本工具用的是其中的 Method 1（固定位长专用计数器）： 把 v7 里 rand_a 的 12 位当成计数器，同一毫秒内每生成一条就加一， 时间戳一变就用随机值重新起头。计数器写满 4096 条就把时间戳往前推 1 毫秒， 保证顺序不会因为回绕而乱掉。
  • 代价是每条只有 62 位真随机（而不是 74 位）—— 用 12 位换「排序即插入顺序」， 对主键场景是划算的。

UUID 里每一位是什么意思

  • 128 位写成 32 个十六进制字符，按 8-4-4-4-12 分五组。
  • 第 13 个字符是版本号（1/4/7）， 第 17 个字符的高位是变体（8/9/a/b 表示 RFC 9562 标准变体）。
  • 所以「这个 UUID 是不是合法的」可以只看这两个字符 —— 校验器里报的版本与变体就是这么来的。
  • UUID 不是加密的，也不是防碰撞的数学保证：它只是「实际用起来不会撞」的随机标识。 需要不可猜测的标识时，用 v4 或 v7 的随机部分，别用自增整数。
